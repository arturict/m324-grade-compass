**Check eurer Antwort:** ✔ Stimmt. Fehlen `compile`-Abhängigkeiten, bricht schon der Build ab. `runtime`-Abhängigkeiten (z. B. ### 4.1.3 Versionen im `pom.xml`

> Weshalb haben die meisten Abhängigkeiten im `pom.xml` keine Version? Wo ist sie festgelegt?

**Eure Antwort:**



<details>
<summary>Lösung zum Vergleichen</summary>

Das `pom.xml` erbt vom **Parent** `spring-boot-starter-parent` (Version `4.1.2`). Dessen Parent ist wiederum `spring-boot-dependencies:4.1.2` (eine *BOM*, Bill of Materials). Dort sind im Abschnitt `<dependencyManagement>` die Versionen aller unterstützten Libraries festgelegt, z. B.:

```xml
<!-- ~/.m2/repository/org/springframework/boot/spring-boot-dependencies/4.1.2/spring-boot-dependencies-4.1.2.pom -->
<h2.version>2.4.240</h2.version>
<postgresql.version>42.7.14</postgresql.version>
...
<dependency>
  <groupId>org.postgresql</groupId>
  <artifactId>postgresql</artifactId>
  <version>${postgresql.version}</version>
</dependency>
```

Vorteil: Spring Boot hat diese Kombination getestet, alle Libraries passen zueinander. Beim Update genügt es, die Parent-Version zu erhöhen. Eine Version im eigenen `pom.xml` braucht es nur für Libraries, die Spring Boot nicht verwaltet (bei uns das Plugin `jacoco-maven-plugin` mit `0.8.14`) oder um eine Version bewusst zu überschreiben (z. B. Property `<postgresql.version>`).

</details>

### 4.1.4 Scopes `runtime` und `test`

> Was bedeuten die Scopes `runtime` und `test`? Weshalb ist die H2-Datenbank im Scope `test` und der PostgreSQL-Treiber im Scope `runtime`?

**Eure Antwort:**



<details>
<summary>Lösung zum Vergleichen</summary>

| Scope | Kompilieren (`src/main`) | Tests | Ausführen / im JAR |
|---|---|---|---|
| `compile` (Standard) | ✅ | ✅ | ✅ |
| `runtime` | ❌ | ✅ | ✅ |
| `test` | ❌ (nur `src/test`) | ✅ | ❌ |

- **`runtime`:** Wird zum Kompilieren nicht gebraucht, aber beim Ausführen. Der Code spricht nur mit JPA/JDBC-Schnittstellen und kennt keine PostgreSQL-Klassen. Den Treiber lädt Spring Boot erst beim Start anhand der `spring.datasource.url` (`jdbc:postgresql://...`). Deshalb `runtime`: Er muss im ausgelieferten JAR sein, aber niemand kann im Code versehentlich PostgreSQL-spezifische Klassen verwenden.
- **`test`:** Nur beim Kompilieren und Ausführen der Tests verfügbar, nicht im ausgelieferten JAR. Die Tests verwenden eine In-Memory-H2-Datenbank (`src/test/resources/application.properties`: `jdbc:h2:mem:testdb`), damit sie ohne Docker/PostgreSQL laufen. In Produktion wird H2 nie gebraucht, deshalb gehört sie nicht ins JAR (kleiner, weniger Angriffsfläche).

</details>

### 4.1.5 Frontend: `package.json` und `package-lock.json`

> Frontend: Was ist der Unterschied zwischen `dependencies` und `devDependencies`? Wozu dient das File `package-lock.json` und was ist der Unterschied zwischen `npm install` und `npm ci`?

**Eure Antwort:**



<details>
<summary>Lösung zum Vergleichen</summary>

**`dependencies` vs. `devDependencies`:**

- `dependencies` braucht die Applikation zur Laufzeit im Browser, sie landen im Build (`frontend/package.json`: `@angular/core`, `@angular/material`, `rxjs`, …).
- `devDependencies` braucht man nur für die Entwicklung: bauen, testen, linten (`@angular/cli`, `@angular/build`, `typescript`, `eslint`, `vitest`, `prettier`, …). Sie sind nicht Teil des ausgelieferten Builds. Mit `npm ci --omit=dev` können sie weggelassen werden.

**`package-lock.json`:**

In `package.json` stehen nur Versionsbereiche: `^22.2.0` erlaubt jede `22.x.y` ≥ 22.2.0, `~7.8.0` nur `7.8.x`. Das Lock-File hält fest, welche Version **tatsächlich** installiert wurde, für alle Packages inkl. transitiver Abhängigkeiten, mit Download-URL und Prüfsumme (`integrity`). Im Notenkompass: 560 Packages (14 für die Laufzeit, 546 nur für die Entwicklung), z. B. `@angular/core` `^22.2.0` → **22.2.5**, `vitest` `^5.0.0` → **5.1.0**. Es gehört ins Git, damit alle (und die Pipeline) exakt denselben Stand installieren.

**`npm install` vs. `npm ci`:**

| | `npm install` | `npm ci` |
|---|---|---|
| Grundlage | `package.json` (Bereiche) | nur `package-lock.json` |
| Lock-File | darf es anpassen/aktualisieren | wird nie verändert; passt es nicht zu `package.json` → Abbruch mit Fehler |
| `node_modules` | wird ergänzt | wird zuerst komplett gelöscht |
| Einsatz | Entwicklung, Packages hinzufügen/aktualisieren | Pipeline, Docker-Build, reproduzierbare Installation |

</details>

- **Nur Laufzeit-Libraries im JAR:** Im JAR liegen 72 Libraries (`BOOT-INF/lib`): der PostgreSQL-Treiber ist drin, H2, JUnit, Mockito (Scope `test`) und `spring-boot-docker-compose` (optional) nicht.

### 4.2.5 Target `docker-clean`

> Erstelle ein Target `docker-clean`, welches die Container und die Images wieder entfernt.

**Eure Notizen:**



<details>
<summary>Lösung zum Vergleichen</summary>

Im [Makefile](../../Makefile):

```makefile
IMAGE ?= grade-compass-backend
TAG ?= latest
CONTAINERS ?= notenkompass-backend notenkompass-backend-2

.PHONY: test clean coverage linting docker docker-clean

# Entfernt die Backend-Container, die Datenbank (Daten bleiben im Volume) und alle Tags des Images.
# "docker rmi" bricht bei fehlenden Images ab, deshalb nur vorhandene IDs via xargs -r löschen.
docker-clean:
	docker rm -f $(CONTAINERS)
	docker compose -f backend/compose.yaml down
	docker images -q $(IMAGE) | sort -u | xargs -r docker rmi -f
```

| Zeile | Wirkung |
|---|---|
| `docker rm -f $(CONTAINERS)` | stoppt und löscht die Backend-Container (1.0 und 2.0 aus 4.3). `-f` = auch laufende Container |
| `docker compose ... down` | stoppt und löscht den Postgres-Container **und das Netzwerk `backend_default`**. Das **Volume bleibt** (nur `down -v` würde die Daten löschen) |
| `docker images -q $(IMAGE) \| sort -u \| xargs -r docker rmi -f` | löscht **alle Tags** des Images (`latest`, `1.0`, `2.0`). `-q` liefert nur die IDs, `sort -u` entfernt doppelte (1.0 und latest hatten dieselbe ID), `xargs -r` ruft `rmi` nicht auf, wenn nichts gefunden wurde |

**Warum nicht einfach `docker rmi grade-compass-backend:latest`?**
- Das löscht nur einen Tag, `1.0` und `2.0` blieben liegen.
- `docker rmi` gibt bei einem nicht vorhandenen Image einen Fehler zurück, und `make` bricht dann ab. Das Target soll aber auch ein zweites Mal ohne Fehler laufen (idempotent). `docker rm -f` auf einen fehlenden Container gibt dagegen keinen Fehler zurück.

### 4.3.3 Zurück auf den alten Stand (Rollback)

> Version 2.0 macht Probleme. Wie gehst du auf den alten Stand zurück?

**Eure Antwort:**



<details>
<summary>Lösung zum Vergleichen</summary>

**Kurz:** Den Container mit `2.0` stoppen und wieder einen Container aus dem **bestehenden Image `grade-compass-backend:1.0`** starten. Es braucht weder einen neuen Build noch Maven oder Quellcode. Das Image `1.0` ist unveränderlich und liegt noch lokal oder in der Registry.

**Fall A – Parallelbetrieb (wie in 4.3.2):** `1.0` läuft noch auf 8080, also reicht es, `2.0` zu entfernen:

```bash
docker rm -f notenkompass-backend-2
```

**Fall B – `2.0` hat `1.0` ersetzt (normales Deployment):** Container mit dem alten Tag neu starten:

```bash
docker rm -f notenkompass-backend
docker run -d --name notenkompass-backend --network backend_default -p 8080:8080 \
  -e DB_URL=jdbc:postgresql://postgres:5432/gcdb grade-compass-backend:1.0
```

Praktisch durchgespielt:

```
### Simulation Deployment: 2.0 ersetzt 1.0 auf Port 8080
notenkompass-backend  grade-compass-backend:2.0  0.0.0.0:8080->8080/tcp, [::]:8080->8080/tcp
POST 60 Zeichen an 8080 -> HTTP 400
### Rollback auf 1.0
notenkompass-backend
Rollback-Dauer: 12.9 s
notenkompass-backend  grade-compass-backend:1.0  0.0.0.0:8080->8080/tcp, [::]:8080->8080/tcp
POST 60 Zeichen an 8080 -> HTTP 201
```

Die 12.9 s sind fast nur der Start von Spring Boot. Ein neuer Build wäre nicht nötig.

**Voraussetzungen, damit das klappt:**

- **Jede Version bekommt einen eigenen Tag** (`1.0`, `2.0`, …). Gäbe es nur `latest`, würde der Build von 2.0 den Tag überschreiben. Das alte Image wäre dann nur noch als `<none>:<none>` (dangling) vorhanden oder schon gelöscht, und man müsste 1.0 neu bauen.
- Alte Images **nicht sofort löschen** (bzw. in einer Registry aufbewahren).
- Konfiguration (`DB_URL`, …) kommt von aussen als Umgebungsvariable, deshalb läuft dasselbe Image überall.

**Code zurücksetzen:** Der Container-Rollback ist die schnelle Sofortmassnahme. Danach muss auch der Code korrigiert werden, z. B. mit `git revert <commit>`. Das erzeugt einen neuen Commit, der die Änderung rückgängig macht, ohne die History umzuschreiben. Daraus baut man eine neue Version (z. B. `2.0.1`).

**Achtung Daten:** Ein Rollback der Applikation setzt die **Datenbank nicht zurück**. Daten, die 2.0 geschrieben hat, bleiben gespeichert. Hat 2.0 das Schema geändert, passt es eventuell nicht mehr zu 1.0 (→ 4.3.4).

*Weiterführend:* Blue-Green-Deployment (beide Versionen laufen, ein Load Balancer schaltet um, und der Rollback ist nur ein Zurückschalten) oder Canary Release (zuerst nur ein kleiner Teil der Benutzer auf 2.0).

</details>

### 4.3.4 Gemeinsame Datenbank

> Beide Versionen verwenden dieselbe Datenbank. Welche Probleme können entstehen, wenn Version 2.0 das Datenbankschema ändert (z. B. eine Spalte umbenennt)?

**Eure Antwort:**



<details>
<summary>Lösung zum Vergleichen</summary>

**Grundproblem:** Der Code und das Datenbankschema hängen voneinander ab. Mehrere App-Versionen auf derselben DB müssen deshalb **alle** mit dem aktuellen Schema funktionieren. Die DB gibt es aber nur einmal und nur in einem Zustand.

**Praktisch ausprobiert** (Simulation: 2.0 benennt `name` in `title` um, 1.0 läuft weiter):

```bash
docker exec grade-compass-postgres psql -U gcdbUser -d gcdb -c 'ALTER TABLE subject RENAME COLUMN name TO title;'
curl -s -w ' HTTP %{http_code}\n' http://localhost:8080/api/subjects   # Version 1.0
```

```
ALTER TABLE
### 1.0 GET
{"timestamp":"2026-11-26T07:47:56.751Z","status":500,"error":"Internal Server Error","path":"/api/subjects"} HTTP 500
### 1.0 POST
{"timestamp":"2026-11-26T07:47:56.774Z","status":500,"error":"Internal Server Error","path":"/api/subjects"} HTTP 500
```

Log von 1.0:

```
2026-11-26T07:47:56.771Z  WARN 1 --- [grade-compass] [nio-8080-exec-8] org.hibernate.orm.jdbc.error             : ERROR: column s1_0.name does not exist
```

**Rollback hilft nicht:** Beim Neustart von 1.0 versucht Hibernate (`spring.jpa.hibernate.ddl-auto=update`), die fehlende Spalte anzulegen. Das scheitert, weil die Tabelle schon Zeilen hat und die neue Spalte `not null` sein soll:

```
2026-11-26T07:48:12.514Z  WARN 1 --- [grade-compass] [           main] o.h.t.s.i.ExceptionHandlerLoggedImpl     : GenerationTarget encountered exception accepting command : Error executing DDL "alter table if exists subject add column name varchar(255) not null" via JDBC [ERROR: column "name" of relation "subject" contains null values]
2026-11-26T07:48:14.403Z  INFO 1 --- [grade-compass] [           main] c.b.m.g.GradeCompassApplication          : Started GradeCompassApplication in 11.444 seconds (process running for 12.214)
```

Die App meldet „Started“, beantwortet aber jede Anfrage weiterhin mit **500**. Erst als ich die Spalte in der DB von Hand zurückbenannt habe (`RENAME COLUMN title TO name`), lief 1.0 wieder (HTTP 200).

**Mögliche Probleme:**

1. **Alte Version bricht sofort:** 1.0 sucht die Spalte `name`, die es nicht mehr gibt → SQL-Fehler → **500** bei jedem Zugriff, obwohl am Code von 1.0 nichts geändert wurde.
2. **Rollback (4.3.3) funktioniert nicht mehr:** Das alte Image passt nicht zum neuen Schema. Man müsste zusätzlich die **DB zurückmigrieren** (Down-Migration oder Backup einspielen). Daten, die 2.0 inzwischen geschrieben hat, können dabei verloren gehen.
3. **`ddl-auto=update` macht es schlimmer:** Hibernate kann nur hinzufügen, nicht umbenennen, löschen oder Typen ändern. Bei einer Umbenennung entsteht eine **neue, leere Spalte**. Die Daten verteilen sich dann auf zwei Spalten, die alte Spalte bleibt als „Leiche“ liegen, oder es kommt wie oben zu einem Fehler mit `not null`.
4. **Bestehende Daten passen nicht zur neuen Regel:** Über 1.0 wurden Namen mit 60 Zeichen gespeichert (4.3.2). Würde 2.0 die 50er-Grenze auch in der DB erzwingen, scheitert die Migration:

   ```
   BEGIN
   ERROR:  value too long for type character varying(50)
   ROLLBACK
   ```

   (in einer Transaktion getestet, die DB blieb unverändert)
5. **Wettlauf beim Start:** Starten mehrere Instanzen gleichzeitig und ändern alle das Schema, kann es zu Konflikten oder halb ausgeführten Änderungen kommen.
6. **Unterschiedliche Daten je Version:** Schreibt 2.0 in `title` und 1.0 in `name` (z. B. nach einem `update`, das eine neue Spalte angelegt hat), sieht jede Version nur einen Teil der Daten.

**Lösungsansätze:**

- **Abwärtskompatible Migrationen (Expand & Contract, Parallel Change):**
  1. *Expand:* Neue Spalte `title` **zusätzlich** anlegen und Daten kopieren. 2.0 schreibt in beide Spalten, 1.0 funktioniert weiter.
  2. Sobald keine 1.0 mehr läuft: *Contract*, also die alte Spalte `name` in einer späteren Version entfernen.
- **Versionierte Migrationen** mit **Flyway** oder **Liquibase** statt `ddl-auto=update`: Die Schemaänderungen sind dann nachvollziehbar, getestet, im Git und laufen genau einmal.
- **Backup** vor jedem Deployment mit Schemaänderung.
- Für Tests oder Parallelbetrieb: **getrennte Datenbanken** pro Version.

</details>
