> Welche Probleme können auftreten, wenn beim Ausführen von Softwares die notwendigen Abhängigkeiten fehlen?

**Eure Antwort:**

Programm kann nicht kompiliern, es kann aber kompilieren auch wenn die runtime und/oder Test dependencies fehlen.

<details>
<summary>Lösung zum Vergleichen</summary>

**Check eurer Antwort:** ✔ Stimmt. Fehlen `compile`-Abhängigkeiten, bricht schon der Build ab. `runtime`-Abhängigkeiten (z. B. PostgreSQL-Treiber) braucht der Compiler für `src/main` nicht, der Fehler zeigt sich erst beim Start. `test`-Abhängigkeiten (H2, JUnit, Mockito) braucht nur das Kompilieren/Ausführen der Tests (`mvn test` scheitert dann bei `testCompile`). Ergänzend:

- **Build schlägt fehl:** Der Compiler findet Klassen/Packages nicht (z. B. `package org.springframework... does not exist`), es entsteht gar kein ausführbares Programm.
- **Start schlägt fehl:** Die Runtime fehlt (z. B. kein Java 25 installiert → `java: command not found` bzw. `UnsupportedClassVersionError` bei einer zu alten Java-Version).
- **Laufzeitfehler mitten im Betrieb:** Eine Library fehlt erst, wenn sie gebraucht wird, z. B. `ClassNotFoundException` / `NoClassDefFoundError`. Fehlt beim Notenkompass der PostgreSQL-Treiber, startet Spring Boot nicht, weil keine `DataSource` erstellt werden kann.
- **Falsche Version:** Die Library ist da, passt aber nicht (`NoSuchMethodError`, geändertes Verhalten, Sicherheitslücken in alten Versionen).
- **«Works on my machine»:** Auf dem Rechner der Entwickelnden ist zufällig alles installiert, auf dem Server oder bei Kolleg:innen nicht. Ohne festgehaltene Abhängigkeiten ist das schwer nachzuvollziehen und von Hand nachzuinstallieren (bei über 100 Libraries) unrealistisch.

</details>

### 4.1.3 Versionen im `pom.xml`

> Weshalb haben die meisten Abhängigkeiten im `pom.xml` keine Version? Wo ist sie festgelegt?

**Eure Antwort:**



<details>
<summary>Lösung zum Vergleichen</summary>

Das `pom.xml` erbt vom **Parent** `spring-boot-starter-parent` (Version `4.1.2`). Dessen Parent ist wiederum `spring-boot-dependencies:4.1.2` (eine *BOM*, Bill of Materials). Dort sind im Abschnitt `<dependencyManagement>` die Versionen aller unterstützten Libraries festgelegt, z. B.:

```xml
<!-- ~/.m2/repository/org/springframework/boot/spring-boot-dependencies/4.1.2/spring-boot-dependencies-4.1.2.pom -->
<h2.version>2.4.240</h2.version>
<postgresql.version>42.7.14</postgresql.version>
...
<dependency>
  <groupId>org.postgresql</groupId>
  <artifactId>postgresql</artifactId>
  <version>${postgresql.version}</version>
</dependency>
```

Vorteil: Spring Boot hat diese Kombination getestet, alle Libraries passen zueinander. Beim Update genügt es, die Parent-Version zu erhöhen. Eine Version im eigenen `pom.xml` braucht es nur für Libraries, die Spring Boot nicht verwaltet (bei uns das Plugin `jacoco-maven-plugin` mit `0.8.14`) oder um eine Version bewusst zu überschreiben (z. B. Property `<postgresql.version>`).

</details>

### 4.1.4 Scopes `runtime` und `test`

> Was bedeuten die Scopes `runtime` und `test`? Weshalb ist die H2-Datenbank im Scope `test` und der PostgreSQL-Treiber im Scope `runtime`?

**Eure Antwort:**



<details>
<summary>Lösung zum Vergleichen</summary>

| Scope | Kompilieren (`src/main`) | Tests | Ausführen / im JAR |
|---|---|---|---|
| `compile` (Standard) | ✅ | ✅ | ✅ |
| `runtime` | ❌ | ✅ | ✅ |
| `test` | ❌ (nur `src/test`) | ✅ | ❌ |

- **`runtime`:** Wird zum Kompilieren nicht gebraucht, aber beim Ausführen. Der Code spricht nur mit JPA/JDBC-Schnittstellen und kennt keine PostgreSQL-Klassen. Den Treiber lädt Spring Boot erst beim Start anhand der `spring.datasource.url` (`jdbc:postgresql://...`). Deshalb `runtime`: Er muss im ausgelieferten JAR sein, aber niemand kann im Code versehentlich PostgreSQL-spezifische Klassen verwenden.
- **`test`:** Nur beim Kompilieren und Ausführen der Tests verfügbar, nicht im ausgelieferten JAR. Die Tests verwenden eine In-Memory-H2-Datenbank (`src/test/resources/application.properties`: `jdbc:h2:mem:testdb`), damit sie ohne Docker/PostgreSQL laufen. In Produktion wird H2 nie gebraucht, deshalb gehört sie nicht ins JAR (kleiner, weniger Angriffsfläche).

</details>

### 4.1.5 Frontend: `package.json` und `package-lock.json`

> Frontend: Was ist der Unterschied zwischen `dependencies` und `devDependencies`? Wozu dient das File `package-lock.json` und was ist der Unterschied zwischen `npm install` und `npm ci`?

**Eure Antwort:**



<details>
<summary>Lösung zum Vergleichen</summary>

**`dependencies` vs. `devDependencies`:**

- `dependencies` braucht die Applikation zur Laufzeit im Browser, sie landen im Build (`frontend/package.json`: `@angular/core`, `@angular/material`, `rxjs`, …).
- `devDependencies` braucht man nur für die Entwicklung: bauen, testen, linten (`@angular/cli`, `@angular/build`, `typescript`, `eslint`, `vitest`, `prettier`, …). Sie sind nicht Teil des ausgelieferten Builds. Mit `npm ci --omit=dev` können sie weggelassen werden.

**`package-lock.json`:**

In `package.json` stehen nur Versionsbereiche: `^22.2.0` erlaubt jede `22.x.y` ≥ 22.2.0, `~7.8.0` nur `7.8.x`. Das Lock-File hält fest, welche Version **tatsächlich** installiert wurde, für alle Packages inkl. transitiver Abhängigkeiten, mit Download-URL und Prüfsumme (`integrity`). Im Notenkompass: 560 Packages (14 für die Laufzeit, 546 nur für die Entwicklung), z. B. `@angular/core` `^22.2.0` → **22.2.5**, `vitest` `^5.0.0` → **5.1.0**. Es gehört ins Git, damit alle (und die Pipeline) exakt denselben Stand installieren.

**`npm install` vs. `npm ci`:**

| | `npm install` | `npm ci` |
|---|---|---|
| Grundlage | `package.json` (Bereiche) | nur `package-lock.json` |
| Lock-File | darf es anpassen/aktualisieren | wird nie verändert; passt es nicht zu `package.json` → Abbruch mit Fehler |
| `node_modules` | wird ergänzt | wird zuerst komplett gelöscht |
| Einsatz | Entwicklung, Packages hinzufügen/aktualisieren | Pipeline, Docker-Build, reproduzierbare Installation |

</details>

**Eure Antwort – Grösse der Images (`docker images`):**



<details>
<summary>Lösung zum Vergleichen</summary>

```dockerfile
# Teil 1 (build): JAR-File mit Maven und JDK bauen
FROM maven:3-eclipse-temurin-25 AS build
WORKDIR /app

COPY pom.xml .
RUN mvn -B dependency:go-offline

COPY src ./src
RUN mvn -B package -DskipTests


# Teil 2 (Laufzeit): nur Java (JRE) und das fertige JAR-File
FROM eclipse-temurin:25-jre
WORKDIR /app

COPY --from=build /app/target/*.jar app.jar

EXPOSE 8080
CMD ["java", "-jar", "app.jar"]
```

`.dockerignore`:

```
target
.idea
.vscode
```

`target` wird ausgeschlossen, damit lokal gebaute Klassen/JARs nicht in den Build-Kontext gelangen (das JAR wird im Container neu gebaut) und der Kontext klein bleibt.

**Weshalb zwei Teile?**

- **Kleineres Image:** Zum Bauen braucht es Maven, das JDK (Compiler), den Quellcode und alle heruntergeladenen Libraries im Maven-Repository (`/root/.m2`, 131 MB). Zum Ausführen genügen das JRE und das fertige JAR (53 MB). Der erste Teil wird nach dem Build weggeworfen, nur `app.jar` wird mit `COPY --from=build` übernommen.
- **Sicherer:** Im ausgelieferten Image gibt es keinen Compiler, kein Maven und keinen Quellcode (geprüft: `which javac mvn` → nicht vorhanden). Weniger Software heisst weniger mögliche Sicherheitslücken.
- **Keine Abhängigkeiten auf dem Build-Rechner nötig:** Java und Maven müssen lokal nicht installiert sein, der Build läuft überall gleich.
- **Nur Laufzeit-Libraries im JAR:** Im JAR liegen 72 Libraries (`BOOT-INF/lib`): der PostgreSQL-Treiber ist drin, H2, JUnit, Mockito (Scope `test`) und `spring-boot-docker-compose` (optional) nicht.

**Grösse der Images** (`docker images`):

| Image | Grösse |
|---|---|
| `maven:3-eclipse-temurin-25` (Basis Build) | 773 MB |
| `eclipse-temurin:25-jre` (Basis Laufzeit) | 503 MB |
| Build-Stage allein (`docker build --target build`), entspricht einem Image mit nur einem Teil | 1.11 GB |
| **`grade-compass-backend:latest`** (zweistufig) | **599 MB** |

Das zweistufige Image ist nur rund 96 MB grösser als das JRE-Basisimage (JAR mit 53 MB + Layer), aber fast halb so gross wie ein einstufiges Image mit Maven/JDK.

</details>

### 4.2.3 Backend und Datenbank im selben Netzwerk

> Starte die Datenbank mit dem Compose-File im Backend (`backend/compose.yaml`) und das Backend als Container im selben Docker-Netzwerk. Rufe `http://localhost:8080/api/subjects` auf. Wie heisst das Netzwerk und weshalb darf in der `DB_URL` nicht `localhost` stehen?

**Eure Antwort – Name des Netzwerks:**



**Eure Antwort – Weshalb nicht `localhost`?**



<details>
<summary>Lösung zum Vergleichen</summary>

**Befehle** (im Hauptverzeichnis):

```bash
docker compose -f backend/compose.yaml up -d
docker network ls

docker run -d --name notenkompass-backend --network backend_default \
    -p 8080:8080 \
    -e DB_URL=jdbc:postgresql://postgres:5432/gcdb \
    grade-compass-backend:latest

curl http://localhost:8080/api/subjects
```

**Ausgabe:**

```
 Network backend_default Creating
 Network backend_default Created
 Container grade-compass-postgres Started
```

```
c.b.m.g.GradeCompassApplication          : Started GradeCompassApplication in 6.311 seconds (process running for 6.72)
```

```
$ curl -s -w '\nHTTP %{http_code}\n' http://localhost:8080/api/subjects
[]
HTTP 200
```

**Name des Netzwerks:** `backend_default`. Docker Compose erstellt pro Projekt ein Netzwerk mit dem Namen *Ordner des Compose-Files* + `_default` (Ordner `backend`). Im Netzwerk ist die Datenbank per DNS unter dem Service-Namen `postgres` und dem Container-Namen `grade-compass-postgres` erreichbar (`docker inspect` → `DNSNames: [grade-compass-postgres postgres ...]`).

**Weshalb nicht `localhost`?** Jeder Container hat seinen eigenen Netzwerk-Stack. `localhost` zeigt im Backend-Container auf den **Backend-Container selbst**, dort läuft aber keine Datenbank. Die Port-Freigabe `5432:5432` im Compose-File gilt nur für `localhost` des **Hosts**, nicht für andere Container. Deshalb muss die `DB_URL` den Namen der Datenbank im Docker-Netzwerk verwenden: `jdbc:postgresql://postgres:5432/gcdb`. Der Standardwert in `application.properties` (`${DB_URL:jdbc:postgresql://localhost:5432/gcdb}`) passt nur, wenn das Backend direkt auf dem Host läuft (`mvn spring-boot:run`).

Ausprobiert mit `-e DB_URL=jdbc:postgresql://localhost:5432/gcdb`: Der Container beendet sich (`Exited (1)`):

```
WARN 1 --- [grade-compass] [           main] org.hibernate.orm.jdbc.error             : Connection to localhost:5432 refused. Check that the hostname and port are correct and that the postmaster is accepting TCP/IP connections.
Caused by: java.net.ConnectException: Connection refused (connect failed)
ERROR 1 --- [grade-compass] [           main] o.s.boot.SpringApplication               : Application run failed
```

Benutzer und Passwort müssen nicht übergeben werden, die Standardwerte in `application.properties` (`gcdbUser` / `gcdbPassword123!`) stimmen mit `backend/compose.yaml` überein.

</details>
