### 2.1.4 Testarten zuordnen

> Ordne die vorhandenen Testklassen einer Testart zu: Unit Test, Controller Test, Repository Test oder Integration Test. Woran erkennst du die Testart im Code?

| Testklasse | Testart | Erkennbar an |
|---|---|---|
| `SubjectServiceTest` | Unit Test| Testet die Service-Logik ohne Controller oder Repository |
| `GradeServiceTest` | Unit Test | Testet die Service-Logik ohne Controller oder Repository |
| `CreateSubjectRequestTest` | Unit Test | Testet die Validierung der Request-Klasse |
| `SubjectControllerTest` | Controller Test | Testet die Endpunkte des Controllers |
| `SubjectRepositoryTest` | Repository Test | Testet die Datenbankoperationen des Repositories |
| `SubjectIntegrationTest` | Integration Test | Testet das Zusammenspiel von Controller, Service und Repository |
| `GradeCompassApplicationTests` | (Unit Test?) | Testet, ob der Spring Boot Kontext korrekt geladen wird | 

**Woran erkennt man die Testart?**
- Unit Tests testen einzelne Klassen oder Methoden isoliert, oft mit Mock-Objekten.
- Controller Tests testen die Endpunkte eines Controllers, oft mit MockMvc.
- Repository Tests testen die Datenbankoperationen eines Repositories.
- Integration Tests testen das Zusammenspiel mehrerer Komponenten (Controller, Service, Repository).
- Tests wie `GradeCompassApplicationTests` prüfen, ob der Spring Boot Kontext korrekt geladen wird, und werden manchmal als Smoke Tests oder Kontext-Tests bezeichnet.

> **Hinweis:** Die Zuordnung stimmt. `GradeCompassApplicationTests` ist aber kein Unit Test, sondern ein **Integration Test** (Smoke Test): `@SpringBootTest` startet die ganze Applikation.
> Die Frage «Woran erkennst du die Testart im Code?» zielt auf die Annotationen über der Klasse:
> - Unit Test: kein Spring, `@ExtendWith(MockitoExtension.class)` mit `@Mock` / `@InjectMocks` (oder gar keine Annotation wie bei `CreateSubjectRequestTest`)
> - Controller Test: `@WebMvcTest(...)`, `MockMvc`, Service mit `@MockitoBean` gemockt
> - Repository Test: `@DataJpaTest`, echtes Repository mit `@Autowired`, H2-Datenbank
> - Integration Test: `@SpringBootTest` (ganze Applikation), nichts gemockt

### 2.4.3 Exception beim Speichern

> Das Repository wirft beim Speichern eine Exception (z. B. weil die Datenbank nicht erreichbar ist). Schreibe einen Test, der erwartet, dass der Fehler an den Aufrufer weitergegeben wird. Was stellst du fest? Finde die Ursache und korrigiere den Code.

**Testmethode:** `create_saveFails_propagatesException` (`save` wirft `RuntimeException("DB nicht erreichbar")`, erwartet wird genau diese Exception).

**Was stellst du fest?** Der Test war zuerst rot (`Expecting code to raise a throwable`). Der Service gab trotz Fehler eine Note zurück (`id = 0`), der Controller hätte `201 Created` geantwortet, obwohl nichts gespeichert wurde.

**Ursache:** Leerer `catch`-Block in `GradeService.create`: `try { grade = repository.save(grade); } catch (Exception e) { }` verschluckt jeden Fehler. SonarQube meldet dieselbe Stelle als `java:S108` (siehe 3.2.4).

**Korrektur (Datei und Änderung):** [GradeService.java](../src/main/java/ch/bbzw/m324/grade_compass/grade/GradeService.java), `try/catch` entfernt:

```java
grade = repository.save(grade);
```

Jetzt kommt die Exception beim Aufrufer an, Spring antwortet mit 500.

### 2.6.2 Note für ein Fach, das nicht existiert

> Was passiert, wenn eine Note für ein Fach erstellt wird, das gar nicht existiert? Schreibe einen Test, der das aktuelle Verhalten dokumentiert. Ist dieses Verhalten sinnvoll? Begründe.

**Testmethode:** `create_unknownSubject_isCurrentlyAccepted`

**Aktuelles Verhalten:** `201 Created`, die Note wird mit `subjectId = 999` gespeichert, obwohl es dieses Fach nicht gibt.

**Sinnvoll? Begründung:** Nein. `subjectId` ist in `Grade` nur eine Zahl (`Long`), keine Verknüpfung (`@ManyToOne`). Es gibt weder einen Fremdschlüssel in der Datenbank noch eine Prüfung im Service. So entstehen Noten, die keinem Fach gehören. Besser: im `GradeService` mit `SubjectRepository.existsById` prüfen und 404/400 zurückgeben, und in der DB einen Fremdschlüssel setzen. Der Testname «isCurrentlyAccepted» zeigt, dass er das heutige Verhalten dokumentiert und bei einer Korrektur angepasst werden muss.

Gemessen am 2026-11-26 mit `make test` (nach den Ergänzungen):

| Testklasse | Testart | Laufzeit |
|---|---|---|
| `GradeCompassApplicationTests` | Integration (`@SpringBootTest`) | 19.9 s |
| `GradeIntegrationTest` | Integration (`@SpringBootTest`) | 3.3 s |
| `SubjectControllerTest` | Controller (`@WebMvcTest`) | 1.6 s |
| `GradeControllerTest` | Controller (`@WebMvcTest`) | 1.4 s |
| `SubjectRepositoryTest` | Repository (`@DataJpaTest`) | 1.3 s |
| `GradeServiceTest` | Unit | 0.6 s |
| `SubjectIntegrationTest` | Integration (`@SpringBootTest`) | 0.5 s |
| `SubjectServiceTest` | Unit | 0.3 s |
| `CreateSubjectRequestTest` | Unit | 0.1 s |

**Langsamste Klasse:** `GradeCompassApplicationTests`, obwohl ihr einziger Test (`contextLoads`) leer ist.

**Weshalb?** `@SpringBootTest` startet die ganze Applikation (alle Beans, JPA/Hibernate, H2, Web). Diese Klasse läuft als erste und bezahlt den Start. Spring speichert den gestarteten Kontext zwischen (Context Caching): `SubjectIntegrationTest` mit derselben Konfiguration braucht danach nur 0.5 s. Unit Tests starten gar kein Spring und brauchen Millisekunden.

**Lässt sich das ändern?** Ja:
- Den leeren `contextLoads`-Test löschen: Die Integration Tests prüfen den Start der Applikation ohnehin.
- So viel wie möglich als Unit Test oder Slice-Test (`@WebMvcTest`, `@DataJpaTest`) testen, nur wenige `@SpringBootTest`.
- In allen `@SpringBootTest`-Klassen dieselbe Konfiguration verwenden (keine unterschiedlichen `@MockitoBean`/Properties), damit Spring den Kontext wiederverwenden kann und ihn nur einmal startet.

## 2.8 Zusatzaufgabe: Integration Test mit Datenbank im Container

> Die Tests laufen mit einer In-Memory-Datenbank (H2). In Produktion wird jedoch PostgreSQL eingesetzt. Ein Integration Test soll deshalb gegen eine echte PostgreSQL-Datenbank laufen, welche für den Test in einem Container gestartet und danach wieder beendet wird. Dazu wird die Library Testcontainers verwendet.

### 2.8.1 Dependencies

> Ergänze die notwendigen Dependencies im `pom.xml`.

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-testcontainers</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>testcontainers-junit-jupiter</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>testcontainers-postgresql</artifactId>
    <scope>test</scope>
</dependency>
```

Ohne Version: Spring Boot 4.1.2 verwaltet Testcontainers 2.0.5 in seiner BOM (vgl. 4.1.3). In Testcontainers 2 heissen die Module `testcontainers-…`, und `PostgreSQLContainer` liegt im Package `org.testcontainers.postgresql`.

### 2.8.2 `SubjectPostgresTest`

> Schreibe eine Testklasse `SubjectPostgresTest`, welche einen Container mit `postgres:18` startet. Teste, dass ein Fach gespeichert und wieder gelesen werden kann und dass ein doppelter Name abgelehnt wird.

Datei: [SubjectPostgresTest.java](../src/test/java/ch/bbzw/m324/grade_compass/subject/SubjectPostgresTest.java)

| Fall | Testmethode | Erledigt |
|---|---|---|
| Fach speichern und wieder lesen | `saveAndRead_returnsStoredSubject` | [x] |

`@Testcontainers` + `@Container` starten den Container vor den Tests und entfernen ihn danach. `@ServiceConnection` ersetzt die H2-Verbindung aus `src/test/resources/application.properties` durch die des Containers. Docker muss laufen.

### 2.8.3 Wann lohnt sich das?

> Weshalb ist ein solcher Test langsamer als die bisherigen Tests? Wann lohnt er sich trotzdem?

**Weshalb langsamer?** Vor dem ersten Test muss Docker einen Container starten (gemessen: `postgres:18` in 3.4 s, dazu der Hilfscontainer `ryuk`), PostgreSQL muss bereit sein, und Spring startet einen eigenen Kontext für diese Verbindung. Die ganze Klasse brauchte am 2026-11-26 rund 34 s, die H2-Tests nur Sekunden. Beim ersten Mal kommt noch der Download des Images dazu.

**Wann lohnt er sich?** Wenn das Verhalten der echten Datenbank zählt: Constraints und Fehlermeldungen, SQL-Dialekt, Datentypen, Migrationen, Unterschiede zwischen H2 und PostgreSQL (z. B. Gross-/Kleinschreibung). Typisch nicht bei jedem Speichern im Editor, sondern in der Pipeline vor dem Deploy: Er findet Fehler, die mit H2 grün wären und erst in Produktion auffallen würden.
